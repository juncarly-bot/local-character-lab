# Design notes - 2026-09-16

## Room composition

- Default conversational experience uses 3 regular characters in the room.
- Maximum remains 4 simultaneous characters.
- The 4th seat is treated as a dynamic Guest Slot.
- Current topic, Interest, Relationship, Desire, Mood, and time of day influence who wants to enter.
- A character whose preferences strongly match the current topic should become much more likely to occupy the Guest Slot.
- UI should include explicit Invite and Exit controls.
- Invite lets the user bring in a favorite character, subject to life-state rules.
- Invite may give a very small positive Relationship effect, with cooldown / anti-farming protection.
- Exit should not strongly damage long-term Relationship because it is primarily a UI action.

## Relationship inactivity behavior

Affection may slowly decline when a character is not spoken with for a long time, but this must not erase a close relationship.

Initial rule:

```text
if affection > 80 and long inactivity:
    affection slowly approaches 80

if affection <= 80:
    no passive inactivity decay
```

Familiarity and Trust do not normally decrease merely because time passes without conversation.
Tension decays with time.

## Avoid equal knowledge across all characters

Interest and Expertise are explicitly separate.

- Interest = how much the character likes / wants to join a topic
- Expertise = how deeply the character understands that domain
- Knowledge Access = whether the character knows a specific fact / event
- Confidence = how certain the character is
- Source = model prior / memory / conversation / news / retrieval

Knowledge Access states:

- UNKNOWN
- HEARD
- KNOWN
- DETAILED

This allows one character to explain, another to ask, another to react, and another to remain unsure even though all characters share the same base model.

## Interest / Expertise configuration without huge manual work

Do not require manual configuration for every topic.

User configures:

1. Broad domains
2. A small number of distinctive topics
3. Explicit exceptions only when needed

Example UI:

```text
興味

[大分類]
科学          75
技術          60
ゲーム        90
食べ物        55
旅行          65

[特徴的な話題]
物理          95
宇宙          90
車            20

[自動推定された興味]
温泉          72
AI            68
数学          82
```

Fallback order for unknown topics:

```text
Explicit Topic Setting
→ Semantic Similarity
→ Domain Setting
→ Character Background
→ Personality / Default
```

Embedding similarity can infer that `gravitational_waves` is close to physics / astronomy without requiring a dedicated hand-written setting.

Automatically inferred interests are stored separately from user-defined values. `source: user` must not be overwritten by automatic inference.

## Knowledge depth

Expertise limits how much specialized knowledge a character should volunteer.

Conceptual levels:

- Level 0: question / backchannel only
- Level 1: common knowledge
- Level 2: somewhat detailed
- Level 3: introductory university-level
- Level 4: specialized explanation

The shared base model may internally know more, but the character should not automatically expose knowledge beyond its profile.

## Conversation Acts

To avoid conversations becoming a knowledge showcase, each utterance gets a conversational role before generation.

v1 acts:

- knowledge
- question
- agreement
- counterpoint
- backchannel
- personal_reaction
- topic_shift
- silence

Example in a physics conversation:

```text
TT: high expertise -> knowledge
SAYO: high interest / medium-low expertise -> personal_reaction
A: low expertise -> question
TT: answer
SAYO: agreement / backchannel
```

## Knowledge cooldown

Avoid:

```text
new knowledge
→ new knowledge
→ new knowledge
→ new knowledge
```

After a `knowledge` act, prefer 1-2 turns of reaction / question / counterpoint / backchannel before another unrelated new fact is introduced.

If the user explicitly asks for a detailed explanation, this cooldown can be relaxed.

## News / realtime information

Recent news can become conversation material.

Architecture:

```text
Internet
→ background News Collector
→ News Cache
→ topic tagging
→ Character Interest matching
→ Knowledge Access / Desire
→ Conversation
```

Three information layers:

1. model prior for stable/general knowledge
2. News Cache for recent topics
3. Live Retrieval only when current-state verification is actually needed

Do not give every News Card to every character at the same depth.

Example:

```text
Space news
TT: strong match -> DETAILED
SAYO: medium match -> HEARD / KNOWN
A: weak match -> UNKNOWN
```

This naturally creates explanation, surprise, questions, and knowledge sharing between characters.

## Latency strategy

Latency is treated as a major design constraint.

Processing priority:

```text
Deterministic code
→ Embedding / similarity
→ Optional lightweight model
→ Main 8B-class model
```

A smaller Qwen-class model may later handle topic classification, simple Conversation Act classification, short summaries, or importance estimation, but it should not become a mandatory v1 dependency before profiling proves it is needed.

The main model should remain focused on final character utterances and difficult semantic interpretation.

News gathering and summarization should normally happen in the background so foreground chat can read from local cache.
