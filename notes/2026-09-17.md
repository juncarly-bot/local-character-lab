# Design notes - 2026-09-17

## Conversation Director v1 direction

Conversation Director is the orchestration layer that decides who speaks, whether silence is valid, and which Conversation Act should be used before the main local model generates the actual line.

Conceptual flow:

```text
new utterance
→ Conversation Analysis
→ Presence / Guest Slot check
→ per-character speak_score
→ primary speaker selection
→ Conversation Act selection
→ Knowledge / Expertise depth guard
→ main local model generates the line
→ optional second reaction
→ continue_score
→ continue or SILENCE
```

### Speaker selection

`speak_score` should combine signals such as:

- direct address from the user
- current Desire
- topic Interest
- Relationship
- initiative
- talkativeness
- Mood
- current conversational relevance
- recent-speaker penalty
- fatigue / low social energy

Expertise alone must not dominate speaker selection. A highly knowledgeable character should not automatically answer every relevant message.

Direct user address gets a strong override. If the user asks a specific character, that character should normally respond first unless a life-state or other hard constraint prevents it.

Silence is a valid Director output when no character has a sufficiently strong reason to speak.

### Conversation Act selection

Speaker selection and utterance role are separate decisions.

Current v1 acts:

- `knowledge`
- `question`
- `agreement`
- `counterpoint`
- `backchannel`
- `personal_reaction`
- `topic_shift`
- `silence`

Character traits should bias acts rather than force them.

Examples:

- high Interest + low Expertise + high curiosity -> question / personal_reaction
- high Expertise + high relevance -> knowledge / counterpoint
- high emotionality -> personal_reaction
- high assertiveness + disagreement signal -> counterpoint
- recent knowledge-heavy conversation -> backchannel / question / reaction preferred

For a second responder, prefer a complementary act rather than repeating the first responder's role.

Example:

```text
TT: knowledge
SAYO: question
A: backchannel
```

instead of three consecutive knowledge dumps.

### Recent act history

Keep a short rolling history of recent speakers and Conversation Acts.

Use it to penalize:

- the same speaker dominating several turns
- too many consecutive knowledge acts
- too many consecutive questions
- repetitive conversational patterns

### Conversation continuation

After each generated utterance, evaluate a `continue_score` using factors such as:

- unresolved question
- strong Desire
- conversation energy
- topic Interest
- chain length
- repetition
- fatigue

Autonomous conversation remains bounded. The previously adopted v1 hard limit of roughly 3 generated utterances per autonomous chain still applies before returning to silence / cooldown.

## Topic Lifecycle v1 direction

A Topic is not only a label. It has lifecycle state so the room can continue, expand, shift, or close naturally.

Conceptual state:

```yaml
topic:
  root: black_holes
  current_focus: time_dilation
  depth: 2
  age_turns: 7
  engagement: 78
  novelty_remaining: 45
```

Important fields:

- `root`: broad topic
- `current_focus`: current subtopic
- `depth`: how deeply the conversation has drilled into details
- `age_turns`: utterances spent on the current topic
- `engagement`: whether participants still appear interested
- `novelty_remaining`: how much fresh information can naturally be introduced without turning the conversation into a lecture

### Topic transitions

Director chooses among:

- `CONTINUE`: stay on current focus
- `EXPAND`: move to a nearby subtopic
- `SHIFT`: move to a related or different topic
- `CLOSE`: let the topic end naturally

### Knowledge-loop prevention

To avoid:

```text
new knowledge
→ new knowledge
→ new knowledge
→ new knowledge
```

new factual information consumes `novelty_remaining`.

Questions, reactions, agreement, counterpoints, and backchannels consume little or none.

When novelty is low, reduce probability of additional unrelated knowledge and prefer reaction / shift / close.

If the user explicitly asks for more detail, engagement and available knowledge budget may temporarily increase and the Knowledge cooldown can be relaxed.

A minimal user reaction such as "へえー" must not automatically be interpreted as a request for a deeper lecture.

### Topic fatigue

Characters may maintain temporary per-topic fatigue.

Long participation in the same subject, repeated same-focus discussion, or low personal Interest can increase topic fatigue.

High topic fatigue can:

- reduce speak_score
- reduce knowledge-act probability
- increase topic-shift probability
- slightly increase leave_score

Even a favorite topic should not continue forever.

### Topic transition and Guest Slot

When Topic Lifecycle changes the current topic, Presence / Guest Slot scoring should be reevaluated.

A new topic may attract a different fourth character whose Interest strongly matches the new subject.

## Topic Proposal / Conversation Seed v1

The user explicitly approved the proposed Seed source design.

A Conversation Seed is not a finished line. It is a structured reason / topic candidate that a character may want to bring up later.

Example:

```yaml
id: seed_123
owner: sayo
source: news
topic: astronomy
subtopic: telescope_result
target: null
strength: 78
freshness: 91
importance: 55
knowledge_access: HEARD
created_at: ...
expires_at: ...
status: pending
```

The final wording is generated only when the Seed is actually used, so Mood, current room members, Relationship, and recent conversation can shape the line.

### Seed sources

The approved v1 source set is:

- `interest`: something from the character's own favorite topics
- `news`: recent news / realtime material from News Cache
- `memory`: follow-up to a previous conversation or promise
- `relationship`: something the character wants to ask / tell a specific person
- `environment`: time of day, weather, season, local context, etc.
- `random_thought`: lightweight everyday chatter without requiring a major reason

The `random_thought` source is intentional. Not every autonomous conversation should be a callback, important memory, or news briefing.

### Seed generation examples

Interest:

```text
high game Interest
→ possible game-related Seed
```

News:

```text
News Collector
→ News Card
→ Interest matching
→ character-specific Knowledge Access
→ News Seed
```

Memory:

```text
USER yesterday: "明日テスト"
→ follow-up memory
→ next-day Seed: ask how the test went
```

Relationship:

```text
strong Relationship + unresolved subject
→ Seed directed at a particular character / user
```

Environment:

```text
late evening / rain / season change
→ lightweight contextual Seed
```

Random thought:

```text
"最近甘いもの食べてないな"
```

### Seed selection timing

Having a Seed does not mean the character speaks immediately.

Director should evaluate a proposal score using signals such as:

- Seed strength
- Interest
- freshness
- initiative
- silence pressure
- Relationship relevance

and penalties such as:

- current topic still has high engagement
- high intimacy / serious discussion
- conflict
- recent topic shift
- fatigue

A serious user conversation should suppress unrelated casual Seeds.

### Seed lifetime

Seeds require expiration / decay.

Suggested qualitative policy:

- news: fast decay
- random thought: fast decay
- interest: medium decay
- relationship: medium decay
- memory follow-up: slow decay

Statuses:

- `pending`
- `used`
- `expired`
- `dismissed`

Do not repeatedly reuse the same News ID or identical Seed.

### Active Seed cap

Keep only a small number of active Seeds per character, roughly 3-7 in v1.

This keeps selection explainable and prevents the Seed queue from becoming an RSS backlog.

### Multiple competing Seeds

When several characters have viable Seeds, avoid strict deterministic highest-score selection every time.

Use weighted selection among strong candidates so higher-scoring Seeds are more likely but not guaranteed to win.

This gives the room some natural variation while remaining interpretable in Developer Mode.

### Seed owner does not equal expert

A character may bring up a subject without being the most knowledgeable person in the room.

Example:

```text
SAYO saw only a headline -> Knowledge Access = HEARD
TT read the article -> Knowledge Access = DETAILED
```

SAYO can still introduce the topic, after which TT may become the explainer.

This is desirable because it produces natural roles such as introducer, expert, questioner, and reactor.

## Current integrated conversation loop

The emerging room architecture is now:

```text
Character Profiles
  ├ Interest
  ├ Expertise
  ├ Personality
  ├ Values
  └ Relationships

Memory / News / Environment
            ↓
      Conversation Seeds
            ↓
     Conversation Director
            ↓
   Topic Lifecycle + Presence
            ↓
 Speaker + Conversation Act
            ↓
 Knowledge Access / Depth guard
            ↓
       main local model
            ↓
       character utterance
            ↓
 Conversation Analysis / Events
            ↓
 Mood / Relationship / Memory
```

This creates a feedback loop where characters can independently bring material into the room without giving every character identical knowledge or forcing constant chatter.

## Speech Style System v1 adopted

The user approved the proposed Speech Style architecture as the production v1 direction and requested it be preserved in full.

A character's voice must not be reduced to a signature ending or catchphrase. Speech is modeled as four layers:

```text
Speech Identity
Speech Tendencies
Signature Expressions
Speech Examples
```

Hard rules include first-person pronouns, address rules, and forbidden expressions. Soft rules include sentence endings, catchphrases, rhythm, sentence length, warmth, directness, and playfulness.

Signature expressions must have frequency / weight / cooldown control so a character does not repeat the same ending every line.

Current speech at runtime is resolved from:

```text
Character Identity
+ Relationship
+ Mood
+ Conversation Act
+ Current Topic
= Current Speech Style
```

The Context Builder selects only the relevant speech slice and a small number of matching example lines for the current Conversation Act / Mood before calling the main local model.

### Adopted East-North-Japan older-sister / Itako reference profile

The proposed 東北イタコ型 profile is accepted as the first official Character Profile / Speech Style reproducibility test case.

Core direction:

- calm, warm older-sister presence
- socially comfortable but not endlessly talkative
- gentle and relatively polite
- can tease close partners lightly
- listens before pushing her own opinion
- does not pretend to know unknown information
- signature endings such as `ですわ`, `ですの`, `かしら` are optional and frequency-controlled, never forced every sentence
- first person `わたくし`
- relationship growth changes distance and playfulness without replacing the base personality
- Mood changes sentence length, directness, emotional expression, initiative, and catchphrase frequency

The full adopted numeric profile, Speech Profile, example lines, Relationship modifiers, Mood modifiers, runtime prompt construction example, and editable Profile UI are recorded in `docs/SPEECH_STYLE_SYSTEM.md`.

This document is now the canonical design for character speech reproduction.
