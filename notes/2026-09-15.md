# Design notes - 2026-09-15

## What was decided

- Separate the character project from 新躍進政策 for now.
- Use one shared 3B-class local model rather than one model per character.
- Plan for roughly 10 registered characters, with at most 4 simultaneously active in one room.
- Characters may talk to each other even when the user says nothing.
- Speaker order must not be a fixed A -> B -> C -> D loop. Silence is a valid outcome.
- Characters should be able to enter and leave the room autonomously.
- Life cycle v1 is intentionally simple: `SLEEP` / `FREE`.
- Entering, invitations, and autonomous conversation are normally available only during `FREE`.
- Relationship state is directional: `A -> B` and `B -> A` are different.
- Long-term relationship axes are Familiarity, Affection, Trust, and Comfort.
- Affection uses `0-100` and never becomes negative.
- Tension is temporary and should decay over time; memories of the event may remain.
- Relationship Tags describe the kind of bond, while numeric axes describe its current depth/state.
- Initial relationship values should be configured rather than starting everyone from zero.
- Personality parameters should include sociability, initiative, curiosity, emotionality, humor, and assertiveness.
- Conversation behavior should include talkativeness, interruption, topic_change, and silence_tolerance.
- Interests use per-topic scores and should be user-extensible rather than a fixed closed list.
- Current topic + character interests should influence who wants to enter or speak.
- Values should be stored as natural-language statements, not only numeric sliders.
- Autonomous Desires should be generated from personality, interests, values, relationships, memory, and mood.
- Example Desire: remember that the user mentioned a physics problem yesterday, then ask later how it went.
- Character icons in the chat UI should open a detail/editor screen.
- Character Detail should allow checking/editing personality, interests, values, relationships, memory, and behavior parameters.
- Current Desire should normally be visible but not manually edited.
- Developer Mode should show why a character entered, stayed silent, spoke, or left, including score contributions.
- The chat UI can borrow the visual foundation of 新躍進政策, while this project remains an independent Character Engine.

## Character Profile v1 direction

The previously proposed Character Profile structure is accepted as the v1 baseline:

- identity / speech style
- Personality: sociability, initiative, curiosity, emotionality, humor, assertiveness
- Conversation behavior: talkativeness, interruption, topic_change, silence_tolerance
- user-extensible Interests with `0-100` scores
- natural-language Values
- life-cycle settings
- initial directional Relationships

Exact numeric anchors and final serialization schema can be refined later without changing this conceptual structure.

## Conversation-derived systems

Mood, Relationship, Presence, and later Desire should share one interpretation of the ongoing conversation rather than being four unrelated decision systems.

### Mood

Mood changes should be influenced primarily by:

- conversation content / topic
- how much that character likes or dislikes the current topic
- tone and quality of the conversation
- time spent participating in the conversation
- current local time / proximity to sleep time
- the character's Personality

Mood should normally drift over time rather than jumping dramatically after every individual line.

### Relationship growth

Relationships may improve through conversations the character genuinely enjoys.

The type of conversation determines which axis changes most:

- ordinary shared time -> mainly Familiarity
- enjoyable favorite topic -> mainly Affection / Comfort
- serious consultation or meaningful disclosure -> mainly Trust
- positive long conversation -> Familiarity plus small Affection / Comfort growth

Relationship changes should be evaluated at a conversation-event or session level rather than giving points for every message. This prevents repetitive farming of Affection.

### Presence

Enter/leave decisions should be affected by:

- conversation content / current topic
- topic interest
- who is already in the room and Relationships with them
- how long the room conversation has continued
- how long the character personally has participated
- time of day / proximity to sleep time
- Mood, Personality, Desire, recent presence, and small randomness

Conversation duration must distinguish:

- `room_conversation_duration`: how long the current room conversation has existed
- `participation_duration`: how long a particular character has actually participated

The first is useful for Presence decisions; the second is more appropriate for fatigue, Mood, and Relationship effects.

## Conversation Analysis v1 adopted

Conversation Analysis v1 has been accepted as the shared sensor layer for Mood, Relationship, Presence, and Desire.

### Topics

Use dynamic topic tags with relevance scores rather than a permanently closed category list.

Example:

```json
[
  {"label": "physics", "score": 0.86},
  {"label": "quantum_mechanics", "score": 0.67},
  {"label": "study", "score": 0.42}
]
```

Topic aliases should later be normalized to canonical labels.

### Room atmosphere

Use continuous signals:

- `valence`: `-1.0` to `+1.0`
- `energy`: `0.0-1.0`
- `intimacy`: `0.0-1.0`
- `conflict`: `0.0-1.0`
- `importance`: `0.0-1.0`
- `humor`: `0.0-1.0`

### Interaction Events

Room atmosphere alone is insufficient for Relationship changes, so directional events are also extracted.

Example:

```json
{
  "from": "user",
  "to": "sayo",
  "type": "personal_disclosure",
  "strength": 0.72
}
```

This makes it possible to distinguish events such as USER disclosing a concern to SAYO and SAYO providing support back to USER.

Interaction Events will become major inputs to Relationship and Memory.

### Duration

Continue to distinguish room conversation duration from each participant's actual participation duration.

## Memory direction

The desired experience requires personal knowledge boundaries: a character should not automatically know events they did not witness.

The physical storage design is still open:

- separate Memory Store per character, or
- shared Memory Store with `known_by` / `participants` filtering.

## Next design targets

- Define the official Interaction Event type list.
- Define Conversation Analysis update timing and session boundaries.
- Map Interaction Events to Relationship deltas.
- Decide Mood state representation and transition rules using Conversation Analysis.
- Define enter/leave weighting, duration effects, and cooldowns.
- Decide how often Desire generation runs and which Conversation Analysis signals it uses.
- Finalize the exact Character Profile serialization schema.
- Select actual 3B base model and local runtime when implementation begins.
